# Domaine Keycloak « gimac »

`gimac-realm.json` est produit par `generer-realm-gimac.py` à partir du realm de développement généré par JHipster ; ne pas l'éditer à la main, relancer le script.

Contenu : permissions (`HOM_*`, `CER_*`, `PAR_*`, `INTERNAL_*`) ; quatorze profils composites **par fonction** (D-58) : `ROLE_INGENIEUR_HOMOLOGATION`, `ROLE_CHEF_DES`, `ROLE_RSSI`, `ROLE_CONFORMITE`, `ROLE_DG`, `ROLE_CORRESPONDANT`, `ROLE_CHARGE_DDRM`, `ROLE_CHEF_DDRM`, `ROLE_SNA`, `ROLE_PRODUCTION_MONETIQUE`, `ROLE_POLE_RESEAU`, `ROLE_POLE_SYSTEME`, et le rôle dédié `ROLE_CONDUCTEUR_PROJET` (habilite à conduire tout projet ; le projet lui est confié par désignation) ; quinze utilisateurs de test (`test-*`, les correspondants portant `institution_id`) ; clients `tester-cli`, `homologation-service`, `certification-service`, `participant-service` ; claim `institution_id` dans le jeton.

**Double facteur (D-61).** Flux navigateur `navigateur-gimac` à niveaux d'assurance : niveau 1 mot de passe, niveau 2 mot de passe puis code TOTP. Depuis D-65, seul `tester-cli` passe encore par ce flux et exige le niveau 2 (`minimum.acr.value`) ; `web_app` pose `acr` 2 par l'octroi direct à deux facteurs (voir ci-dessous) ; Keycloak pose le niveau atteint dans le claim `acr`, contrôlé par OPA à la passerelle et par chaque service. `tester-cli` accepte l'autorisation par appareil (RFC 8628) pour les contrôles cURL. Import vérifié le 29/09/2026 sur Keycloak 26.7.4 (distribution officielle) : domaine, flux, profil utilisateur, thème et comptes de service chargés sans erreur.

**Administration depuis la plateforme (D-62).** Permissions `IAM_*` et `PLATFORM_*` ; profil `ROLE_SUPER_ADMIN` (toutes les permissions d'administration, sans le rôle technique `ROLE_ADMIN`, qui ouvre le CRUD généré et les points `/management` des services) et profil `ROLE_RSSI` étendu (administration des comptes sauf l'attribution d'un profil privilégié, politique de sécurité, messagerie, supervision en lecture) ; utilisateur de test `test-super-admin`. Client `iam-service` dont le compte de service porte les rôles `realm-management` utiles à MS-IAM (`manage-users`, `view-users`, `query-users`, `query-groups`, `manage-realm`, `view-realm`) ; client `gateway-supervision` (`ROLE_ADMIN`, lecture des points `/management`). Profil utilisateur déclaratif : attributs `institution_id`, `phone_number`, `fonction`, `profil_complet`, `langKey`, `login` modifiables par l'administration seulement (`unmanagedAttributePolicy: ADMIN_EDIT`), l'utilisateur les renseigne par « Mon compte ». Inscription libre fermée, mot de passe oublié réinitialisable, langues fr, en, es ; messagerie de développement vers Mailpit (`messagerie:1025`), reconfigurable depuis la console.

**Thème GIMAC (`themes/gimac`).** Pages de connexion, du second facteur, du mot de passe à renouveler et de la configuration du TOTP (thème `login`, dérivé de `keycloak.v2`) et courriels d'invitation, de réinitialisation et d'essai (thème `email`), conservés pour l'historique : depuis D-65, aucune de ces pages n'est montrée aux utilisateurs et les courriels de la plateforme sont envoyés par MS-IAM, en français, anglais et espagnol, aux jetons de `@gimac/theme` (bleu institutionnel, angles droits, bordures de 1 px, pied de page institutionnel). Monté dans le Compose ; intégré à l'image `Dockerfile` (`registre.gimac.local/des/keycloak:26.7.4-gimac`, avec `gimac-realm.json`) pour Kubernetes. Aperçu : `apercu-connexion.png`.

**Connexion sur la plateforme (D-65, contrat `docs/lot1/connexion.md` §4).** L'utilisateur ne voit jamais une page de Keycloak : la passerelle soumet identifiant, mot de passe et code par l'octroi direct, serveur à serveur.
- Flux `direct-gimac-mot-de-passe` (identifiant, mot de passe) et `direct-gimac-deux-facteurs` (identifiant, mot de passe, `direct-grant-validate-otp` **REQUIRED**).
- Client `gimac-connexion` : confidentiel, octroi direct seul lié au flux mot de passe, secret `${GIMAC_SECRET_CONNEXION}`, mappeur `acr` = « 1 » posé en dur, sans portée `acr` par défaut, jeton de 5 min (session restreinte du premier accès ; MS-IAM y vérifie aussi le mot de passe actuel).
- Client `web_app` : confidentiel, octroi direct seul lié au flux deux facteurs, `standardFlowEnabled` faux, mappeur `acr` = « 2 », sans portée `acr` par défaut, secret `${GIMAC_SECRET_WEB_APP}`.
- Jetons : `acr`, `institution_id` et les rôles et permissions (claim `roles`) figurent dans le jeton d'identité comme dans le jeton d'accès ; le code TOTP est passé à l'octroi direct de `web_app` dans le paramètre `otp` ; la révocation du jeton de rafraîchissement (`/protocol/openid-connect/revoke`) sert à la déconnexion par la passerelle.
- Client `gateway-service` : compte de service portant `INTERNAL_IAM_READ` (état de connexion lu sur MS-IAM), secret `${GIMAC_SECRET_GATEWAY_SERVICE}`.
- Aucune action requise de Keycloak sur les comptes : les actions exigées sont tenues par MS-IAM dans l'attribut `gimac_actions_requises` (déclaré par le profil utilisateur, administration seulement) ; les comptes de test portent `SECOND_FACTEUR`. Mot de passe oublié de Keycloak désactivé (`resetPasswordAllowed` faux) : la réinitialisation passe par le courriel de MS-IAM.
- Sessions : inactivité 1 800 s, durée maximale 36 000 s, jeton d'accès 300 s. Protection contre la force brute active (5 échecs, attente de 15 min), elle s'applique à l'octroi direct. Politique des mots de passe au plancher `length(12) and notUsername(undefined)`, politique OTP `HmacSHA1`, 6 chiffres, 30 s, tolérance d'un pas.
- Extension **`gimac-totp`** (`extensions/gimac-totp`, Maven, Java 21, Keycloak 26.7.4 en `provided`, SPI `RealmResourceProvider`) sous `/realms/gimac/gimac-totp` : `POST /utilisateurs/{id}/totp` `{secret (base 32), code, libelle}` vérifie le code avec la politique OTP du domaine puis crée l'identifiant OTP (secret encodé `BASE32`, code existant remplacé) ; `DELETE …/totp` supprime les codes ; `GET …/totp` → `{configure}`. Jeton porteur vérifié (`AppAuthManager.BearerTokenAuthenticator`), réservé à un compte de service portant le rôle `manage-users` de `realm-management` (`iam-service`) : 401 sans jeton valide, 403 sinon, 404 pour un compte inconnu. Ni secret ni code journalisé. Construite par la première étape du `Dockerfile` et copiée dans `/opt/keycloak/providers`. Tests : `mvn verify` dans `extensions/gimac-totp` (9 tests unitaires, couverture 97 % des lignes, 100 % des branches ; `GimacTotpIT` charge l'extension et le domaine dans un vrai Keycloak 26.7.4 par Testcontainers et éprouve la chaîne complète : 401/403/404, enregistrement du code, octroi direct `acr` 1 sur `gimac-connexion`, `acr` 2 sur `web_app` avec le code).
- Pour le Compose de développement, le jar se construit par `mvn -f infra/keycloak/extensions/gimac-totp/pom.xml package` et se monte dans `/opt/keycloak/providers` ; les variables `GIMAC_SECRET_CONNEXION`, `GIMAC_SECRET_WEB_APP` et `GIMAC_SECRET_GATEWAY_SERVICE` doivent être fournies à Keycloak comme les autres secrets.

Aucun secret : mots de passe et secrets de client sont des variables `${GIMAC_...}` résolues par Keycloak à l'import, à partir du `.env` local créé par `gimac-dev.sh`. Jeton d'un utilisateur de test : `source infra/docker-compose/scripts/token.sh test-chef-ddrm` (niveau 2, par le navigateur) ou `NIVEAU=1 source ...` (niveau 1, pour vérifier les refus). Depuis D-65, les comptes de test configurent leur code TOTP sur la plateforme au premier accès ; `tester-cli` garde le flux navigateur et l'autorisation par appareil pour les seuls contrôles des développeurs.

## Sandbox et mTLS

Le générateur réserve `INTERNAL_IAM_SBX_SAGA` au client `sbx-espace` et donne `INTERNAL_IAM_SBX_INTROSPECT` à `gateway-service` pour la décision MS-IAM sans cache utilisée par le cloisonnement. Les sagas OUVERTURE/MATRICE et le réexamen US-EXI-23 conservent les permissions et profils non SBX ; la validation des verdicts reste interdite aux profils externes.

Le rattachement des jetons de service au certificat client (RFC 8705) reste une configuration de déploiement. Aucune autorité de certification mTLS locale n'est livrée dans cet environnement ; les tests du domaine et Testcontainers ne constituent pas une preuve de mTLS bout en bout ni de raccordement à des serveurs GIMAC réels.

**Rendu PDF des processus (28/10/2026).** Le compte de service `pilotage-service` porte aussi `INTERNAL_DOCUMENT_RENDER`, limité à `POST /api/v1/interne/rendus/pdf` de MS-DOCUMENT pour l'export PDF des instances de processus. Les JSON de domaine sont régénérés par `generer-realm-gimac.py`, jamais édités directement.
